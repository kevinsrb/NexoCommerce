# Phase 3: Orders and Inventory Design

**Status:** Revised after Sentinel NO-GO
**Date:** 2026-10-01

## Scope and non-goals

Phase 3 adds checkout order records and inventory reservations using the existing principal-scoped Cart and Catalog variant model. Orders durably records checkout intent and the order saga; Catalog alone owns stock and reservation lifecycle.

Non-goals: payment authorization/capture, tax, discounts, shipping charges, fulfillment, returns, public order management APIs, inventory receiving, and cross-service distributed transactions.

## Current facts and design assumptions

- Cart is scoped to the authenticated principal; checkout does not accept or depend on a caller-supplied `cart_id`.
- Cart lines identify Catalog variants with `variantId` and quantity.
- Catalog prices are decimal strings. Checkout must preserve and calculate those values without JavaScript floating-point arithmetic.
- Phase 3 adds Cart version/claim metadata and Catalog stock-reservation records. Do not assume Phase 2 already has either capability. These proposed contract additions must be aligned with service owners before implementation.

## Ownership

- **Gateway** forwards the end-user authorization header and trace context unchanged, and enforces the public/private routing boundary. Orders performs local JWT verification and derives the principal identity.
- **Cart** owns the Redis state for the current principal-scoped cart. Phase 3 adds a monotonically increasing version and checkout-claim metadata in the same principal cart key; it atomically claims a version and prevents edits while that claim is active.
- **Catalog** is the sole owner of sellable variants, prices, stock quantities, and the complete reservation lifecycle: reserve, release, expiry, and reservation-aware administrative changes.
- **Orders** owns checkout idempotency/intent, immutable order snapshots, order state, and durable saga progress. It stores Catalog reservation references for recovery, but does not own or mutate reservation state or stock.

No cross-service transaction is assumed. Orders persists intent before asking Catalog to reserve, and retries or compensates using stable operation identifiers.

## Checkout flow and duplicate prevention

1. Client sends `POST /api/checkout` to Gateway with `Authorization: Bearer <JWT>`, a required `Idempotency-Key`, and the expected prices currently displayed for every cart variant; Gateway creates or forwards `x-request-id`.
2. Orders locally verifies the forwarded HS256 JWT using the existing access-token configuration and requires `sub`, `type: access`, and valid `exp`. It derives `principalId` from `sub`, then atomically inserts/claims a durable checkout attempt before any Catalog reserve call. Uniqueness is enforced for `(principal_id, idempotency_key)`. The attempt records a canonical request hash and stable `checkout_attempt_id`. The same key/hash never starts another attempt: it first reconciles the existing attempt and any order with Catalog, then returns that order's *current* lifecycle state; a different hash returns `409 IDEMPOTENCY_KEY_REUSED`.
3. Orders reads the principal-scoped Cart and receives its current `version` and lines `{variantId, quantity}`. It asks Cart to claim that exact version using `checkout_attempt_id`. Cart atomically permits only one active checkout claim for the principal's current cart version. A repeated claim by the same attempt returns the original claim; a competing claim returns conflict. After successful checkout, Cart finalization clears the cart and advances its version, so a second request holding the old version cannot create another order. A stale version returns conflict. While claimed, cart edits fail with `409 CART_CHECKOUT_IN_PROGRESS`.
4. Orders validates quantities and one currency, then reads each variant's canonical sellability and decimal-string price from Catalog. Cart display prices are non-binding; Orders compares each submitted `expectedPrices` value with Catalog's current value. A difference returns `409 CHECKOUT_PRICE_CHANGED` with the current canonical item prices, creates no reservation/order, and releases the Cart claim after recording the failed attempt. The frontend refreshes/reconfirms those prices and retries with a new idempotency key. Orders never silently uses a changed price.
5. Orders persists the normalized variant/quantity lines, submitted expected-price hash, and `RESERVATION_PENDING` saga state before calling Catalog. It calls Catalog once with the stable attempt ID, complete line set, and the canonical prices it just read. Catalog atomically rechecks those prices with stock and sellability; if a price changed between read and reserve, it returns `CHECKOUT_PRICE_CHANGED` with canonical current prices and creates no reservation. Otherwise it reserves all requested variants or none and returns the exact reserved price snapshot, `reservedAt`, and `expiresAt`. Retries with the same attempt ID return that same reservation and snapshot.
6. After Catalog confirms reservation, Orders transactionally persists the order, lines, reservation reference, and `expiresAt` in internal `RECORDING` state. `RECORDING` orders are not visible in customer responses or order views. Orders then calls Catalog's conditional `publish-order` operation with the stable `attemptId` and `orderId`.
7. `publish-order` is the checkout publication linearization point. In the same Catalog row-locked transaction used by the expiry worker, it requires `ACTIVE` and Catalog UTC `< expiresAt`, records the bound order ID and immutable `publicationRevision`, and transitions the reservation `ACTIVE → PUBLISHED` without extending expiry. If expiry acquired the lock first, publication returns `409 RESERVATION_EXPIRED`; Orders transitions the internal record to `EXPIRED` and does not return `PENDING`. If publication acquired the lock first, the expiry worker can only later transition `PUBLISHED → EXPIRED`; its durable expiry event includes `publicationRevision`. Orders atomically records that revision and transitions `RECORDING → PENDING`, then may return the first `201 PENDING` response. Thus the response represents Catalog state at the serialized publication revision; a later expiry is a later lifecycle event, not a stale cached response. Every same-key replay reconciles Catalog's current lifecycle and keeps the stable order ID/snapshot while returning its current state. The successful checkout action remains customer acceptance. Orders then finalizes/clears Cart; retries are idempotent.
8. Insufficient stock, price change, validation failure, or an expired reservation causes Orders to record the stable outcome and release the Cart claim when no active uncertain reservation remains. A price-change retry must use a new idempotency key. If reservation or publication outcome is uncertain, Orders keeps the claim and recovers the same attempt/order rather than creating another one.

### Durable recovery

Checkout attempts move through `CLAIMED → CART_CLAIMED → PREPARED → RESERVATION_PENDING → ORDER_RECORDING → RESERVATION_BOUND → ORDER_PENDING → COMPLETE`. `FAILED` is terminal only after any active Catalog reservation is confirmed released and the Cart claim is released. Expiry may terminally mark an internal recording or visible pending order `EXPIRED`. Attempt/order state changes use transactional compare-and-set/version checks. A recovery worker scans nonterminal attempts and resumes idempotently:

- Before Cart claim: retry reading and claiming the current Cart version for the same attempt.
- After Cart claim but before the Orders record contains its result: retry Cart claim with the same attempt ID to retrieve the same claim/version.
- During/after a Catalog timeout: retry reserve or query reservation status with the same attempt ID; Catalog returns the original outcome rather than reserving twice.
- After reservation but before order persistence: retry creation of the same stable `RECORDING` order. If deliberately abandoned, release through Catalog and wait for confirmed release before releasing the Cart claim or marking `FAILED`.
- After `RECORDING` persistence or uncertain publication: query/retry Catalog using the same `attemptId` and `orderId`. `PUBLISHED` with the same order ID/revision permits `PENDING`; `EXPIRED`/`RELEASED` transitions the internal order to `EXPIRED`, even if it was never visible; unknown status is retried. Never create another order ID for that attempt.
- After `PENDING` persistence but before checkout response or Cart finalization: return `PENDING` only after recording Catalog's publication revision. The expiry worker is serialized after that revision; its later durable event changes the lifecycle to `EXPIRED`. Every same-key replay reconciles and returns the current `PENDING` or `EXPIRED` state rather than replaying the original success envelope blindly. Then retry Cart finalization idempotently.

Transient failures remain recoverable and visible; never discard an uncertain attempt or create a new reservation token to bypass it. Alert on attempts exceeding the recovery age threshold.

## Order and checkout state machines

Phase 3 order states: internal invisible `RECORDING → PENDING → CANCELLED`, and `RECORDING → EXPIRED` or `PENDING → EXPIRED`. A successful checkout creates visible `PENDING` only after Catalog serializes its `ACTIVE → PUBLISHED` publication transition for the stable order ID. Phase 3 has no `PENDING → CONFIRMED` transition. A future Phase 5 may confirm only after a Catalog atomic reservation commit/consume succeeds before expiry; that operation and transition are explicitly out of scope here. On reservation expiry, Catalog releases stock idempotently and emits the authoritative expiry outcome; Orders transitions the corresponding `RECORDING` or `PENDING` order to `EXPIRED` idempotently. Orders does not independently expire or release stock.

Checkout attempt states and recovery rules are defined above. Invalid transitions return conflict. All transitions use compare-and-set/version checks.

## Price snapshots and totals

Cart display prices are non-binding. The checkout request supplies an `expectedPrices` entry `{variantId, price_decimal, currency}` for every current Cart variant. Orders compares currency and exact decimal value with current Catalog prices without floating point; a mismatch returns `409 CHECKOUT_PRICE_CHANGED` with canonical `currentPrices` and no order/reservation. To close the read/reserve race, Catalog also compares the canonical prices in the reserve request inside its all-or-nothing reservation transaction and returns the same error and current canonical prices if any value changed. The frontend refreshes/reconfirms and submits a new checkout with a new `Idempotency-Key`; the changed value is never silently accepted. On successful reserve, Orders snapshots the exact decimal prices returned by Catalog, with `variantId`, currency, quantity, and exact line total. Phase 3 applies no tax, discounts, or shipping: `order total = sum(line quantity × unit price)` in the same currency. Preserve decimal scale/precision from Catalog and serialize the resulting total as a decimal string. Parse and multiply using an exact decimal or base-10 integer-and-scale implementation; never convert price or total to a JavaScript `Number`. Later Catalog price changes do not rewrite an order snapshot.

## Catalog reservations and oversell prevention

Catalog exposes an atomic batch reserve operation over all order variants. In one Catalog database transaction, it locks or conditionally updates variants in stable `variantId` order, verifies each is sellable and sufficiently available, and creates the reservation only if every line succeeds. Availability must never become negative. A stable unique `checkout_attempt_id` is the idempotency token: same token and same normalized lines returns the original reservation; same token with different lines conflicts. Catalog owns the reservation record and state; Orders persists only the returned reservation identifier/reference and saga progress.

Catalog release is conditional and idempotent: `ACTIVE` or `PUBLISHED → RELEASED` restores availability exactly once. Repeated release returns the existing terminal state. Expiry performs the same one-time transition. Reservation states are `ACTIVE → PUBLISHED → EXPIRED` or `ACTIVE|PUBLISHED → RELEASED`; `CONSUMED` is out of scope because fulfillment is out of scope. Orders cannot directly alter these states.

### Reservation-aware Catalog administration

Administrative stock adjustment must use the same Catalog transaction/locking boundary as reservation. A resulting stock quantity may not be lower than nonterminal (`ACTIVE` or `PUBLISHED`) reserved quantity; reject such an update with a conflict and report available/reserved quantities to authorized operators. Variant deletion/replacement is blocked while a nonterminal reservation refers to that `variantId`. A replacement receives a new `variantId`; nonterminal reservations remain attached to the old immutable variant until released/expired. Do not silently transfer reservations or rewrite order snapshots. Catalog's admin API and schema constraints must enforce these rules even when called outside checkout.

## Expiry and release

Catalog records `reservedAt` from its server UTC clock and computes `expiresAt = reservedAt + 15 minutes`; the caller cannot set or override either timestamp. Catalog persists and returns both values. `publish-order` conditionally transitions `ACTIVE → PUBLISHED` only while Catalog UTC `< expiresAt`, stores the bound order ID and `publicationRevision`, and never extends the deadline. The publication and expiry worker lock the same reservation row: if expiry wins, publication fails; if publication wins, a later expiry transitions `PUBLISHED → EXPIRED` and its durable event carries the same revision. Catalog is the expiry source of truth; Orders consumes that event/status idempotently and transitions the corresponding `RECORDING` or `PENDING` order to `EXPIRED`. Unknown event delivery is recovered by querying the same attempt. Orders cannot expire or release stock itself.

## Gateway and private HTTP contracts

Public Gateway contract: `POST /api/checkout`, body `{expectedPrices:[{variantId, price_decimal, currency}]}` (checkout uses the authenticated principal's current Cart). Expected prices must cover each current Cart variant exactly once and are only a comparison against what the customer saw; they are never authoritative charges. Required headers: `Authorization: Bearer <JWT>` and `Idempotency-Key`; `x-request-id` is optional on ingress and generated by Gateway when absent. Phase 3 preserves the existing HS256 access JWT contract: Orders verifies the JWT locally, using the existing access-token verification configuration as Cart does, and requires `sub`, `type: access`, and a valid `exp`. Do not add issuer/audience requirements or a Gateway-signed identity context. Gateway forwards the original `Authorization`, `Idempotency-Key`, and `x-request-id` headers unchanged to Orders. Orders derives `principalId` from verified `sub`; it does not accept identity from the body or caller-supplied identity headers. Public endpoints remain JWT-only and do not accept the internal Cart service token.

Proposed private contracts (all require authenticated service-to-service transport and must not be internet-routable):

- Gateway → Orders: `POST /internal/v1/checkouts`, body `{expectedPrices:[{variantId, price_decimal, currency}]}`, headers original `Authorization`, `Idempotency-Key`, and `x-request-id`. The first successful result is `201` with stable order ID, `PENDING` state, currency, decimal-string total, `expiresAt`, line snapshots, and Catalog `publicationRevision`. A same-key replay first reconciles Catalog expiry and returns `200` with the same order ID/snapshot and its current `PENDING` or `EXPIRED` state; it never replays a stale `PENDING`. A still-uncertain `RECORDING` attempt returns `202 CHECKOUT_PROCESSING` without exposing an order. Price mismatch returns `409 CHECKOUT_PRICE_CHANGED` with `details.currentPrices`.
- Orders → Cart: Orders authenticates with the new `CART_INTERNAL_SERVICE_TOKEN` environment secret; Cart validates the same configured secret. Orders never forwards the user's JWT to Cart. Private `POST /internal/v1/cart/read` requires `{principalId}`; `POST /internal/v1/cart/checkout-claims` requires `{principalId, attemptId, expectedVersion}`; `POST /internal/v1/cart/checkout-claims/complete` and `POST /internal/v1/cart/checkout-claims/release` require `{principalId, attemptId, version}`. Every endpoint requires the service token and `x-request-id`. Read returns `{version, lines:[{variantId, quantity}]}`; claim atomically claims the expected version; complete clears the claimed cart idempotently; release removes an uncompleted claim idempotently. Cart keys state by `principalId`; claim/complete/release additionally require the attempt and version to match the stored claim. The token grants only these Cart checkout operations and is not accepted on public endpoints. Orders forwards the same `x-request-id` to Cart for trace continuity; it is correlation metadata, never identity or idempotency proof.
- Orders → Catalog: `GET /internal/v1/variants/{variantId}` returns authoritative `{variantId, sellable, available, price_decimal, currency}`; `available` is point-in-time only, and reservation is the authoritative check. All public and internal Catalog availability reads expose `available`, never raw `onHand` as purchasable stock. `POST /internal/v1/reservations` accepts `{attemptId, lines:[{variantId, quantity, expected_price_decimal, expected_currency}]}` and atomically reserves all lines; Catalog rechecks expected prices with stock, computes/persists `reservedAt` and `expiresAt`, and accepts no caller expiry field. Price mismatch returns `CHECKOUT_PRICE_CHANGED` and canonical current prices without reserving. `POST /internal/v1/reservations/by-attempt/{attemptId}/publish-order` accepts `{orderId}` and, in the same locked transaction as expiry, requires `ACTIVE` and `now < expiresAt`, writes the bound order ID plus immutable `publicationRevision`, and transitions to `PUBLISHED`; the same order retry returns that publication and another order ID conflicts. `GET /internal/v1/reservations/by-attempt/{attemptId}` returns status, bound order ID, publication revision, price snapshot, `reservedAt`, and `expiresAt`. `DELETE /internal/v1/reservations/by-attempt/{attemptId}` requests conditional idempotent release. Catalog emits durable published-expiry events or exposes status for Orders reconciliation.

Use error body `{code, message, request_id, details?}` without internal exception details. `409 CHECKOUT_PRICE_CHANGED` includes `details.currentPrices:[{variantId, price_decimal, currency}]` for every affected/current line; `409 RESERVATION_EXPIRED` means Catalog could not serialize `publish-order` before expiry, and no `PENDING` order is returned. Expected codes: `400 INVALID_REQUEST`; `401 UNAUTHENTICATED`; `403 FORBIDDEN`; `404 VARIANT_NOT_FOUND`; `409 IDEMPOTENCY_KEY_REUSED`, `409 CART_VERSION_CHANGED`, `409 CART_CHECKOUT_IN_PROGRESS`, `409 CHECKOUT_PRICE_CHANGED`, `409 RESERVATION_EXPIRED`, `409 INSUFFICIENT_STOCK`, `409 RESERVATION_LINES_MISMATCH`; `422 CART_EMPTY`, `422 VARIANT_UNSELLABLE`, `422 MIXED_CURRENCY`; `429 RATE_LIMITED`; `503 DEPENDENCY_UNAVAILABLE`. Gateway preserves known codes and maps unknown upstream errors to generic `503`. `x-request-id` is validated/generated at Gateway and propagated through all calls/logs; it is tracing only, never an idempotency token. Do not log JWTs or full cart contents.

## Schemas and migrations

Orders owns:

- `checkout_attempts(id, principal_id, idempotency_key, request_hash, cart_version, cart_claim_ref, prepared_lines, state, saga_version, reservation_ref, failure_code, created_at, updated_at)` with unique `(principal_id, idempotency_key)`. `request_hash` includes the submitted expected prices; `prepared_lines` persists normalized quantities and the canonical Catalog prices used for an idempotent reserve retry.
- `orders(id, checkout_attempt_id, principal_id, cart_version, state, currency, total_decimal, expires_at, catalog_publication_revision, published_at, created_at, updated_at, version)` with states `RECORDING`, `PENDING`, `EXPIRED`, and `CANCELLED`; `RECORDING` is excluded from every customer-visible projection. Unique `checkout_attempt_id` and unique `(principal_id, cart_version)` prevent duplicate accepted orders; the latter is safe because the Cart version counter is non-reusable.
- `order_lines(id, order_id, variant_id, quantity, unit_price_decimal, line_total_decimal, currency, variant_snapshot)` with positive-quantity checks and FK to order.
- `outbox(id, event_type, aggregate_id, payload, created_at, available_at, attempts, completed_at)` for durable recovery/reconciliation work, indexed by pending work.

Cart's Phase 3 Redis migration uses separate principal-scoped keys; none is a cart ID:

- `cart:data:{principalId}` stores cart lines and has the existing 30-day payload TTL.
- `cart:version:{principalId}` stores the monotonic integer version, has no TTL, is persisted/non-evictable, and is never reset when payload expires. If missing while a payload or claim exists, fail closed and alert; do not initialize it to zero. Migration seeds a counter for every live Phase 2 payload before checkout is enabled.
- `cart:claim:{principalId}` stores the active `{attemptId, version}` claim. It has no TTL while active and retains claim/terminal recovery metadata until Orders completes recovery.

Every Cart operation uses one atomic Lua/script transaction over these keys. Read returns payload lines and the persistent counter value; when payload is absent/expired it returns an empty cart with the last counter value without creating a payload or resetting the counter. A brand-new principal may initialize its counter to zero atomically only when no prior counter, payload, or claim exists; a missing counter alongside payload/claim is an integrity error. Claim requires a present, unexpired, non-empty payload, compares `expectedVersion` to the counter, and atomically stores the claim with that version and removes the payload TTL (`PERSIST`). A repeated claim by the same attempt/version returns the same claim; a competing/stale claim conflicts. While claimed, the payload and claim remain until Orders terminally completes or releases the attempt; no claim lease or payload expiry can silently unlock it.

Every mutation script checks the claim key, rejects edits while a claim is active, changes payload lines, increments `cart:version` in the same transaction, and refreshes the payload's 30-day TTL. Complete requires matching `principalId`, `attemptId`, and claimed version; atomically clears lines, increments the persistent version, records terminal completion, clears the active claim, and applies the normal payload TTL. Release requires the same binding; it preserves lines and version, records terminal release, clears the active claim, and reapplies the normal payload TTL. Terminal retries by the same attempt return the recorded result; stale/mismatched attempts cannot mutate data. Because the counter survives payload expiry and increments on edits/completion, a version from an expired payload can never identify a later cart payload. Orders keeps its unique `(principal_id, cart_version)` accepted-order constraint on this non-reusable version.

An absent/expired payload is not implicitly created by claim: private read returns an empty cart with its persistent version and claim returns `404 CART_NOT_FOUND`, which Orders maps to `422 CART_EMPTY` for checkout. A later cart mutation increments the retained counter before writing its new payload. If Orders crashes while a cart is claimed, the non-expiring claim and payload remain while its recovery worker resumes the same durable attempt and calls complete or release. Operators must not delete claimed keys or version counters as routine cleanup; recovery/repair must resolve claims first. Public Cart routes remain JWT-only and use the same atomic claim-aware scripts.

Catalog owns stock and `stock_reservations(attempt_id, reservation_id, variant_id, quantity, state, unit_price_decimal, currency, reserved_at, expires_at, bound_order_id, publication_revision, published_at, created_at, updated_at)` with unique attempt/variant constraints and durable expiry state. Persisting the reserved price snapshot, serialized publication, and server timestamps makes reserve/publish retries return the original outcome. Publication is conditional on `state = ACTIVE` and Catalog UTC `< expires_at`; it does not change the deadline. Catalog reservation requests and reads use the same stable Orders `checkout_attempt_id` as the API's `attemptId`. Orders does not create a competing reservation table or migration in Catalog's database.

Catalog stock invariant is `onHand >= reserved >= 0`; `available = onHand - reserved`. Phase 3 migration adds `onHand` and `reserved`, initializes each existing stock quantity into `onHand`, and sets `reserved = 0`, then validates constraints before switching reads/writes. All public and internal availability reads expose `available`, never raw `onHand` as purchasable stock. Authorized admin views may show `onHand`, `reserved`, and `available`; admin writes may change `onHand` only if the resulting value is at least current `reserved`. Reservation increases `reserved`; release/expiry decreases it exactly once. Admin deletion or variant replacement is rejected while any nonterminal reservation refers to the variant; replacement uses a new `variantId` and never transfers reservations.

Catalog batch reserve takes `attemptId` and all normalized `{variantId, quantity}` lines. In one database transaction it locks variants in stable order, checks sellability and `available`, and either reserves every line or none. It writes a durable reservation record with Catalog-computed expiry in the same transaction. Retries with the same `attemptId` and identical lines return the stored reservation; mismatched lines conflict. Existing stock is migrated as unreserved stock; do not infer reservations from carts.

Phase 3 migrations add Orders `RECORDING`/publication columns and Catalog `bound_order_id`/`publication_revision`/`published_at` plus a conditional publish operation and durable expiry events. Cart migration seeds a persistent no-TTL version counter for every live principal payload, deploys the three-key atomic scripts, and protects counters from eviction with Redis persistence/backup; counters are never deleted when 30-day payloads expire. A missing counter for a live payload or claim fails closed. Deploy Catalog stock/publish/expiry support first, then Cart counter/claim migration, then Orders recovery and Gateway routing disabled. Enable checkout only after counter migration/health checks and Catalog expiry-event recovery are verified. Keep the existing 30-day TTL for unclaimed payloads; active claims remove it until terminal recovery. Do not create cart IDs or convert cart lines to SKU; use principal scope and `variantId`.

## Tests and rollout

Cover exact decimal multiplication/serialization without floating point; intent uniqueness and concurrent idempotency claims; two different keys racing for the same Cart version; payload expiry followed by cart recreation proving version never repeats and stale claims fail; concurrent claim/mutation/complete scripts; stale-version and edit-during-claim behavior; all-or-none concurrent Catalog reserve proving no oversell; serialized `publish-order` racing expiry (each row-lock ordering yields either `PUBLISHED`/one `PENDING` publication revision or `RESERVATION_EXPIRED`, never both); recovery from unknown publication outcome; a later bound expiry transitioning visible `PENDING → EXPIRED` idempotently; a same-key replay after expiry returning the same order ID/snapshot with `EXPIRED`, never stale `PENDING`; Phase 3 never auto-confirming; idempotent reserve/release/expiry and exact 15-minute UTC deadline; reservation-aware admin adjustment and variant replacement; crash/timeout recovery at every checkout boundary; confirmed-release-before-claim-release; JWT validation and spoofed identity rejection; contract/error mapping; and end-to-end success, empty cart, unsellable variant, changed expected price returning canonical prices without an order/reservation, new-key price reconfirmation, insufficient stock, duplicate request, and Cart finalization retry.

Roll out behind a server-side flag by cohort. Apply additive Orders/Catalog migrations and reconcile stock; deploy Catalog reserve/publish/release/expiry with durable publication-revision expiry events; migrate live Cart payloads to persistent non-expiring version counters and three-key atomic scripts; then deploy Orders recovery and Gateway routing disabled. Verify counters survive payload expiry/restart, the publish/expiry lock ordering is observable, and RECORDING rows remain invisible. Enable internally and then by cohort. Monitor duplicate/replay rates, cart version integrity errors, checkout-attempt recovery age, RECORDING age, active reservation age, publication/expiry ordering, release/expiry reconciliation failures, stock invariant violations, and outbox lag. Keep a kill switch for new checkout while Cart claim recovery and Catalog release/expiry continue. Rollback disables new checkout first; retain schemas and data until all attempts and reservations are resolved.

## Sentinel review: resolved technical decisions

The following NO-GO findings are resolved by this design: intent is durable and uniquely claimed before Catalog reserve; principal Cart version claims prevent duplicate checkout; Catalog alone owns reservation and stock lifecycle; Catalog admin stock/variant operations respect active reservations; Catalog computes expiry; Gateway has an explicit JWT/header identity contract; prices remain exact decimal strings with no tax/discount/shipping or floating point; contracts use the current principal-scoped Cart and `variantId`.

## Coordinator-approved product semantics

- A successful `POST /api/checkout` creates a visible `PENDING` order; checkout itself is customer acceptance. Phase 3 does not automatically confirm orders. Phase 5 may transition `PENDING → CONFIRMED` only after its future Catalog atomic reservation commit/consume succeeds before expiry.
- Catalog reservation TTL is 15 minutes. On expiry, Catalog releases the reservation idempotently and Orders transitions `PENDING → EXPIRED`.
- Cart display prices are non-binding. Orders uses the current Catalog price only after it matches the submitted expected price; otherwise checkout returns `409 CHECKOUT_PRICE_CHANGED` with canonical current prices, and the frontend must refresh/reconfirm and use a new idempotency key.
- Catalog server UTC is the exact time source: `expiresAt = reservedAt + 15 minutes`. Catalog returns `expiresAt` for the client countdown; the client never sets it.
